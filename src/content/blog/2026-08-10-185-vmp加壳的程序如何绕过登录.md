# 一次「响应重放」式的登录绕过：HT_26-0215 Bypass 拆解

> 本文基于本地工作区中的 `ht26_bypass.py`、早期版本快照、`ht26_capture.py` 以及 2026-06-30 的成功/失败抓包日志完成。所有结论都能在对应文件或日志行中找到依据；属于推断的部分会单独标注。文中的目标地址与授权服务域名以 `TARGET_HOST`、`LICENSE_API_BASE` 占位符表示。

## 结论先行

这套 bypass 并没有破解目标的密码算法，也没有伪造账号。它做的是四件事：

1. **在网络层替换服务端响应**：把「登录失败」的 TCP 响应体，在 `recv` 返回给目标进程之前，覆盖成事先抓到的「登录成功」密文。
2. **接管登录后的 UI 流程**：自动点掉「登录成功」「账号在其他地方登录」等 `MessageBox`，再把被对话框流程挡住的主窗口强行显示出来。
3. **阻止程序自杀**：目标在鉴权失败后会调用 `TerminateProcess` 结束自己，bypass 把终止句柄改成 `NULL`，让这次终止调用失败。
4. **伪造进程内时间**：把目标看到的系统时间稳定在 2026-06-30，绕过依赖本地日期的到期校验，同时保持时间缓慢前进，避免超时循环空转。

一句话概括：**它不是「破解」，而是「重放 + 环境伪装」**。真正的突破口是目标服务端的成功响应可以被原样重放，加密本身并没有被攻破。

## 1. 先分清两层授权

这个工作区里其实有两套完全独立的授权：

```
┌─────────────────────────────────────────────────────────┐
│ 外层：启动器自己的卡密体系（作者卖卡用）                  │
│   HT26_Bypass_Launcher.exe                               │
│   activate / check / heartbeat  ──►  LICENSE_API_BASE    │
│   离线 Ed25519 永久卡 license.permanent.json             │
└──────────────────────────┬──────────────────────────────┘
                           │ 授权通过后启动并注入
                           ▼
┌─────────────────────────────────────────────────────────┐
│ 内层：目标程序 HT_26-0215.exe 的登录校验                 │
│   TCP TARGET_HOST:9002                                   │
│   01/17 前置检查 → 01/15 在线检查 → 01/01 登录           │
│   ← 本文的主角：Frida 运行时响应替换                     │
└─────────────────────────────────────────────────────────┘
```

外层解决「谁能用这个工具」，内层解决「目标程序愿不愿意进入功能面板」。两层之间没有信任传递：启动器授权通过，只是允许启动器去启动 HT；HT 自己的登录照样要过。所以 bypass 的核心不在启动器，而在 `ht26_bypass.py` 注入到 HT 进程里的那段 Frida 脚本。

## 2. 侦察阶段：先写一个「只监听」的抓包器

`ht26_capture.py` 是整套工程的起点，头部注释写得很明确：

> 注册/登录纯监听，不篡改 / 不拦截 / 不强制比较。

它 hook 的范围比最终 bypass 宽得多：

- `ws2_32!send` / `ws2_32!recv` / `WSASend` / `WSARecv`
- `WinHTTP` / `WinINet` 系列（目标还有 HTTP 请求）
- `MessageBoxA/W`（记录弹框文本）
- 常见字符串比较函数与 `memcmp`（用来定位「密码错误」这类分支）

抓包时按时间顺序记录了完整的调用栈、socket、目标地址和原始 hex。工作区里保留了两份关键日志：

- `logs/ht26_capture_20260630_231603.log`：成功登录
- `logs/ht26_capture_20260630_231717.log`：失败登录

成功和失败各抓一遍、逐字节对比，是整个项目最关键的一步。没有这两份日志，后面的固定样本无从谈起。

## 3. 协议长什么样

### 3.1 帧格式

从抓包可以直接读出帧结构：

```
请求（send 缓冲区）:
┌──────────────┬──────────┬──────────────────────────┐
│ body 长度 4B │ op 2B    │ 加密 body                │
│ 小端          │ 01 17 等 │                          │
└──────────────┴──────────┴──────────────────────────┘

响应（recv 分两次读）:
第一次：┌──────────────┐
        │ body 长度 4B │  例如 0d 00 00 00 = 13
        └──────────────┘
第二次：┌──────────────────────────┐
        │ body（定长，加密）        │
        └──────────────────────────┘
```

抓包里的实际样本：

```
send  len=85  hex=51000000 0117 cac1b43ccf14976f09ca2b33fb4a...
              └─ 81 ─┘ └op┘ └──────── 加密体 ────────┘
recv  len=4   hex=0d000000            ← 长度头，13 字节
recv  len=13  hex=39f5f51e9675be1751c29a6817
```

### 3.2 op 表与固定样本

`ht26_bypass.py` 里维护了三张「成功响应」黄页：

| op | 脚本里的语义 | 请求体长度 | 成功响应长度 | 成功响应 body |
|---|---|---|---|---|
| `01/17` | 前置检查 | 81 | 13 | `39f5f51e9675be1751c29a6817` |
| `01/15` | 心跳 / 在线检查 | 57 | 20 | `39f5f51e9377ba1248c382690e1fa1930ce014e4` |
| `01/01` | 登录 | 79 | 36 | `39f5f51e9374be6253c7eb6a6b17dd9708ee62e411bb79b9668b0bb2534d4834f6d80cf3` |

失败样本则短得多：

| op | 失败响应长度 | 失败响应 body |
|---|---|---|
| `01/17` | 4 | `c70a0ae1` |

几个值得注意的观察：

1. **每条 op 用一条独立 TCP 连接**。成功日志里 01/17、01/15、01/01 分别落在 socket 1188、1220、1252 上，不是一条长连接复用。这也是后来 socket 状态机可以只记「该 socket 最后一次 send 的 op」的原因。
2. **成功响应都以同一 4 字节 `39f5f51e` 开头**，而失败响应没有这个前缀。它可能是协议魔数，也可能是固定密钥流的前 4 字节；本文不对加密算法做猜测，因为 bypass 根本不需要解密。
3. **请求密文的头部也高度一致**（`cac1b43c cf14976f ...`）。这暗示请求侧存在固定密钥、固定会话参数或固定请求头；无论属于哪种，都不影响重放。
4. **响应长度与 op 一一对应**。这让「改长度头」成为可能：把 `04 00 00 00` 改成 `0d 00 00 00`，再把 4 字节失败体换成 13 字节成功体即可。

## 4. Bypass 的骨架：注入 + socket 状态机

### 4.1 定位与注入

`ht26_bypass.main()` 用 psutil 精确匹配进程名 `ht_26-0215.exe`，不用模糊匹配——因为启动器自身打包后也可能叫 `ht26_bypass.exe`，模糊匹配会打到自己身上。拿到 PID 后 `frida.attach(pid)`，加载脚本，等待消息。

启动器 `ht26_launcher.py` 负责把这一步串起来：UAC 提权 → 校验卡密 → 确保 HT 已启动（没有就 `Popen` 拉起，等 3 秒）→ 调用 `ht26_bypass.main()` 注入。启动器窗口必须保持打开，因为 Frida 会话挂在启动器的进程里，关掉启动器等于拔掉注入。

### 4.2 以 socket 为键的状态机

JS 侧对每个 socket 维护一个状态：

```js
function st(sock) {
    var k = String(sock);
    if (!states[k]) states[k] = { op: "", expect: "idle", wantedLen: 0, dst: "" };
    return states[k];
}
```

`connect` 记录目标地址；`send` 时从缓冲区偏移 4、5 的位置取出 op，把状态置为 `expect="len"`；`recv` 返回后分两种情况：

- 返回 4 字节：当作长度头处理；
- 状态是 `body`：当作响应体处理。

```js
onLeave: function(retval) {
    var rv = retval.toInt32();
    if (rv <= 0) return;
    var state = st(this.sock);

    if (state.expect === "len" && rv === 4) {
        patchRecvHeader(this.sock, this.buf, rv, state);
        return;
    }
    if (state.expect === "body") {
        patchRecvBody(this.sock, this.buf, this.reqLen, rv, retval, state);
        return;
    }
    ...
}
```

这里有一个隐含假设：**长度头必须单独一次 `recv` 返回 4 字节**。日志里服务端确实分两次发送，所以稳定；如果哪天 TCP 合并成一次返回 17 字节，这条路径就匹配不上，会退化到「只记录不修改」。这是当前实现的一个脆弱点，后面会再提。

### 4.3 先改长度头

```js
function patchRecvHeader(sock, bufPtr, rv, state) {
    var arr = readBytesCompat(bufPtr, rv);
    var lenVal = u32le(arr);
    var success = chooseSuccessBody(state.op);
    if (!success) return false;

    if (shouldPatchHeader(state.op, lenVal)) {
        writeBytesCompat(bufPtr, le32(success.length));
        state.expect = "body";
        state.wantedLen = success.length;
        state.patchBody = true;
        return true;
    }
    ...
}
```

`shouldPatchHeader` 的逻辑很直接：只要当前 op 有成功样本，且长度不等于样本长度，就改写长度。比如 01/17 的失败响应是 4 字节，会被改成 13 字节。

### 4.4 再改响应体

```js
function patchRecvBody(sock, bufPtr, reqLen, rv, retval, state) {
    var arr = readBytesCompat(bufPtr, rv);
    var success = chooseSuccessBody(state.op);
    if (!success) { state.expect = "done"; return false; }

    var needPatch = state.patchBody || rv !== success.length || !sameBytes(arr, success);
    if (!needPatch) { state.expect = "done"; return false; }

    if (reqLen < success.length) {
        // 调用方给的缓冲区太小，写不下，只能放弃
        state.expect = "done";
        return false;
    }

    writeBytesCompat(bufPtr, success);
    retval.replace(success.length);   // 把 recv 的返回值改成新长度
    state.expect = "done";
    return true;
}
```

两处细节决定了成败：

- **`reqLen` 检查**：目标调用 `recv` 时传入的缓冲区大小必须不小于成功样本长度。这里是 13/20/36 字节，实际客户端通常给几 KB，所以能过；但如果某个版本把缓冲区卡得很紧，就会写不进去。
- **`retval.replace(success.length)`**：只改内存不够，还要把 `recv` 的返回值从 4 改成 13，否则目标仍然只读 4 字节。这是整个 patch 的点睛之笔。

### 4.5 为什么这样能成功

从抓包和代码可以反推出三个前提，缺一不可：

1. **响应可重放**：服务端返回的成功报文里没有与本次请求绑定的随机挑战（nonce）或时间戳签名。同一份 13/20/36 字节密文，换一台机器、换一个账号、隔几个月仍然被客户端接受。
2. **客户端只校验格式与结果**：从行为上看，客户端拿到这批字节后就继续走登录流程，没有把它与本次请求做绑定校验。具体是解密后读标志位还是别的判据，外部无法确认，但这不影响「重放成立」这一结论。
3. **鉴权状态只存在于这一次握手**：01/17、01/15、01/01 各自独立连接，成功后客户端进入功能面板；后续不再有强绑定校验。

因此这套方案的本质是**利用了服务端协议缺少挑战-应答绑定**，而不是破解了加密。加密算法、密钥、明文结构全都不需要知道——抓包看到的密文直接原样回放即可。

### 4.6 局限

- 只覆盖 `01/17`、`01/15`、`01/01` 三个 op；`01/04`、`01/1f` 只记录不修改。
- 依赖固定密文样本。服务端换密钥、换协议版本、加随机字段，样本立即失效。
- 依赖「4 字节头单独到达」和「缓冲区足够大」两个时序/内存假设。
- 只对 `ws2_32` 的 `recv` 生效；如果目标改用 `WSARecv`、IOCP 或 HPSocket 封装层，就抓不到。

## 5. 登录之后的四场战役

网络响应改完，只是「让服务端说 yes」。客户端还有一整套防御性流程，需要逐个拆掉。

### 5.1 弹框：JS 只观察，Python 动手

`MessageBoxA/W` 被 hook，但 JS 侧不直接点按钮，只做识别和上报：

```js
var successBox = (textStr.indexOf("登录成功") >= 0 || ... || uTypeN === 0x2040);
var kickBox = (textStr.indexOf("挤下线") >= 0 || textStr.indexOf("其他地方登录") >= 0 || ...);
if (successBox) send({kind:"login_success_box"});
if (kickBox) send({kind:"kick_box_detected", ...});
```

真正点掉弹框的是 Python 侧的守护线程 `auto_close_msgboxes()`：

- 用 `EnumThreadWindows` 枚举目标进程各线程的窗口，只找类名 `#32770` 的对话框。注释里说明了原因：全系统 `EnumWindows` 会干扰全屏 DirectDraw 游戏的渲染。
- 读取标题和子控件文本，命中「登录成功」「到期」「挤下线」「在其他地方登录」「即将关闭」等关键词。
- 用 `PostMessageW(hwnd, WM_COMMAND, IDOK, 0)` 模拟点击「确定」。
- 登录后常驻监控：游戏运行时 5 秒轮询，平时 2 秒，避免频繁打扰游戏。

JS 端还保留了一条 `login_success_box` 事件，用来触发两个后续动作：启动弹框守护线程、等待并恢复主窗口。

### 5.2 防自杀：把终止句柄改成 NULL

当目标判定鉴权失败、或运行中的在线检查不通过时，它会调用 `TerminateProcess(GetCurrentProcess(), ...)` 结束自己。bypass 在 `kernel32!TerminateProcess` 和 `ntdll!NtTerminateProcess` 两层都下了钩子：

```js
onEnter: function(args) {
    if (!bypassCheck()) return;          // 保护窗口结束就放行
    var h = args[0].toInt32();
    if (h === -1 || h === 0xffffffff) {  // 伪句柄 -1 = 当前进程
        args[0] = ptr(0);                // 改成 NULL，让 syscall 返回无效句柄
    }
}
```

为什么两层都要 hook：`kernel32!TerminateProcess` 内部会继续调用 `ntdll!NtTerminateProcess`，只 hook 上层挡不住直接走 ntdll 的路径。为什么不 hook `ExitProcess` / `RtlExitUserProcess`：那些是正常退出路径，全部拦掉会导致关不掉程序。

当前版本（与 v8 的差异只在这里）对 `handle == -1` 的终止**一律改写**，不再做调用栈过滤；早期版本曾用 `stackHasTarget` 只拦来自目标模块的调用，但实际运行中会漏掉一些路径。

### 5.3 时间伪造：不是改系统时间，而是骗进程

成功样本抓取于 2026-06-30。当前日期已经是 11 月，同样的成功报文如果直接回放，客户端很可能会在本地日期校验处判「已到期」。这一点是从时间锚点与代码注释推断的——抓包里没有可直接读出的到期字段。所以 bypass 把目标进程内的时间钉回 2026-06-30。

实现方式是 hook 一组时间 API，在**返回时改写输出结构**，只在目标进程内生效：

| 模块 | 函数 | 改写目标 |
|---|---|---|
| kernel32 | `GetSystemTime` | `SYSTEMTIME`（UTC） |
| kernel32 | `GetLocalTime` | `SYSTEMTIME`（本地） |
| kernel32 | `GetSystemTimeAsFileTime` | `FILETIME` |
| kernel32 | `GetSystemTimePreciseAsFileTime` | `FILETIME` |
| msvcrt / ucrtbase / msvcr* | `time` / `_time32` / `_time64` | `time_t` 返回值与输出指针 |

锚点值：

```js
var FAKE_UTC   = { year: 2026, month: 6, dow: 2, day: 30, hour: 4,  min: 0, sec: 0, ms: 0 };
var FAKE_LOCAL = { year: 2026, month: 6, dow: 2, day: 30, hour: 12, min: 0, sec: 0, ms: 0 };
var FAKE_UNIX_SEC = 1782792000;                 // 2026-06-30T04:00:00Z
var FAKE_FT_LO = 0xEBEDA000, FAKE_FT_HI = 0x01DD0844;
```

三个设计选择很关键：

- **时间要「动」，但不能跨天**。实现用 `GetTickCount` 的差值做偏移，再对 12 小时取模：进程启动时是 6/30 12:00，之后每毫秒前进，12 小时后回到 12:00。这样既不会让时间静止，也不会跨到 7 月 1 日。
- **不能冻结时间**。代码注释记录了实测结果：固定不动的假时间会让 HT 的超时循环忙等，表现为约两个 CPU 核心长期满载。这也是 v8 从「固定值」改成「滚动值」的直接原因。
- **刻意避开 `ntdll!NtQuerySystemTime`**。它是高频调用，hook 它会显著拖慢登录，收益却有限；只 hook 高层 API 已经覆盖目标的实际调用路径。

### 5.4 主窗口恢复：等 `WTWindow` 出现

正常情况下，「登录成功」的对话框关闭后，客户端才异步创建主窗口 `WTWindow`。bypass 的 `wait_and_restore_main_window()` 用 150ms 轮询枚举目标进程窗口，一旦发现可见的 `WTWindow` 就立即：

- `EnableWindow(hwnd, TRUE)`
- `ShowWindow(hwnd, SW_RESTORE)` / `SW_SHOW`
- `SetForegroundWindow(hwnd)`

如果 15 秒内没等到，就退化成对所有顶层窗口和子控件做一次全量恢复。这解释了使用说明里那句「登录成功弹框会被自动关闭，等约 20 秒功能面板出现」。

## 6. 生命周期：保护窗口与游戏监控

早期版本最大的问题是「保护过头」：`TerminateProcess` 全拦、时间全程伪造，导致用户正常关程序也关不掉，或者游戏退出后 HT 卡死。后来的版本引入了 `BYPASS_ACTIVE`：

```js
var BYPASS_ACTIVE = true;
function bypassCheck() { return BYPASS_ACTIVE; }

rpc.exports = {
    releaseProtection: function(reason) {
        disableFakeTimeHooks(reason);
        BYPASS_ACTIVE = false;
        ...
    }
};
```

所有敏感 hook（时间、终止拦截）在生效前都先问一句 `bypassCheck()`；保护窗口结束后一律放行。

有意思的是，**当前版本实际上从不调用 `releaseProtection()`**。v6 里游戏进程消失时会通过 rpc 释放保护、允许 HT 正常退出；当前版本把这个逻辑改成了「只记录日志，HT 保持运行，等待下一次启动游戏」。`GAME_PROCESS_NAMES` 里包含 `ra2ol.exe`、`HTplatform.exe`、`HTEsport.Client.exe`，监控线程只负责感知游戏的出现与消失。最终保护窗口跟随 HT 进程的生命周期：HT 退出 → Python 主循环检测到 → Frida detach。

这里还留着一处注释与实现不一致：`watch_game_process` 的调用处注释仍写着「游戏消失时释放保护」，但函数体只打印日志，并没有调用 rpc。读旧代码时容易按注释误判实际行为。

这个演进说明了一个工程事实：**绕过本身不难，难的是让绕过在真实使用场景里不误伤正常流程**。用户关游戏、关程序、再次开局、长时间挂机，每一个场景都可能踩到 hook 的副作用。

## 9. 这套方案脆弱在哪

站在分析视角，它的失效条件非常清晰：

**客户端侧**

- 服务端响应加入 nonce / 时间戳 / 会话绑定 / 签名，固定密文立即作废。
- 协议版本变更、op 重编号、密钥轮换，三张样本表全部失效。
- 目标改用 `WSARecv`、IOCP 或自研网络层，`ws2_32!recv` hook 直接落空。
- 目标加入 Frida 检测、模块完整性校验、时间 API 统一走直接 syscall，注入本身就会被发现或绕过。
- 目标把鉴权状态改成「每次操作都回服务端确认」，一次性握手成功不再够用。

**服务端侧（防御建议）**

- 成功响应必须绑定本次会话：nonce + 服务端签名 + 过期时间，客户端校验签名而不是只读标志位。
- 把 01/17、01/15、01/01 合并成一次带挑战的握手，禁止跨连接复用结果。
- 对同一机器码/账号的并发连接做限制，异常时服务端主动失效会话。
- 定期轮换协议密钥，让旧密文样本自然过期。

**工程侧的两个真实教训**

1. **固定时间会制造忙等**。任何靠「时间不前进」实现的绕过，都可能让目标的超时循环变成死循环。滚动时间、小步前进是更稳的做法。
2. **全系统窗口枚举会干扰全屏游戏**。`EnumWindows` 在 DirectDraw 全屏下会造成明显卡顿，改用 `EnumThreadWindows` 只触碰目标进程，是这套工程里最有价值的细节之一。

## 10. 尾声

把整条链路摊开看，HT_26-0215 的 bypass 并不神秘：

- 用「只监听」的抓包器拿到成功/失败样本；
- 用 Frida 在 `recv` 返回前替换长度头和响应体；
- 用弹框自动确认、终止拦截、时间伪造、窗口恢复补齐客户端流程；
- 用启动器把注入、授权、生命周期包成一个用户可双击的 exe。

它真正利用的缺陷只有一个：**服务端把「成功」做成了可重放的静态密文**。加密强度再高，只要响应没有会话绑定，抓一次就能用一辈子。对做协议设计的人来说，这比任何逆向技巧都更值得记住。
