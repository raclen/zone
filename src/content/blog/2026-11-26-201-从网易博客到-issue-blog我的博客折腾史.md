回头看，自己写博客已经有十多年的时间了。

从最早的网易博客，到 Hexo、FarBox，再到 GitHub Issues，期间换过好几次平台。每一次迁移，背后都有不同的原因：有的是为了更好的写作体验，有的是为了方便管理文章，也有的是因为原来的平台停止服务。

如今，随着 AI 工具的发展，我干脆自己做了一个博客项目，把以前一直想要的功能整合到了一起。

## 2012 年：从网易博客开始

最早接触博客是在 2012 年，当时使用的是网易博客：

`29793.blog.163.com`

那时候的网易博客还支持部分自定义 HTML，可以自己折腾一些页面效果。我记得当时还会通过添加 `audio` 标签给博客设置背景音乐，打开博客就能播放音乐，感觉特别炫。

网易博客还有一个很有意思的功能：**随便逛逛**。

不知道看什么的时候，就点一下这个按钮，随机进入其他人的博客，看看别人写的内容、设计的页面。现在回想起来，那时候的博客社区氛围还是挺有意思的。

不过，后来网易博客逐渐退出历史舞台，最终关闭了服务。

## 2014—2015 年：迁移到 Hexo，开始 Markdown 写作

工作之后，平时需要记录大量的代码片段，网易博客的编辑器逐渐满足不了我的需求。

当时网易博客不支持代码块这样的标签，我只能通过自定义 CSS 来调整代码片段的显示效果，让它看起来更舒服一些。

在浏览其他技术博客的过程中，我逐渐意识到，Markdown 很可能会成为未来技术写作的主流方式。

于是，我开始尝试使用 Hexo 搭建博客，并将文章迁移到了 GitHub Pages：

https://hello-javascript.github.io/

Hexo 确实解决了代码高亮、Markdown 写作和自定义主题等问题，但使用一段时间后，我发现它也有一个明显的问题：**写文章太麻烦了。**

每次写文章都需要打开本地编辑器，创建文件，按照指定的目录结构保存，再执行命令生成页面。插入图片也不够方便，文章写完之后还要执行 Git 提交和推送。

对于一个程序员来说，这些操作当然不算什么技术难题，但如果只是想随手记录一些东西，就显得有些繁琐了。

我希望写博客应该是一件简单的事情，而不是每次写文章之前，都要先完成一套操作流程。

## 2016—2021 年：遇见 FarBox

后来，我接触到了 FarBox。

它给我的感觉是：终于有一个平台，把我想要的写作体验和技术自由结合起来了。

FarBox 使用 Markdown 语法写文章，同时支持 Jade 模板，可以自定义博客的前端样式和布局。更重要的是，文章、模板以及相关文件都可以保存在本地，数据和前端代码都有较高的可控性。

它还提供二级域名，也支持绑定自己的域名，每月有 100GB 流量额度，超出后另外收费。

当时的价格也很便宜，36 元使用 5 年，算下来一年还不到 8 元。

从 2016 年一直使用到 2021 年，这算是我使用时间比较长的一款博客服务了。

相比 Hexo，FarBox 的写作体验轻松了很多，也不需要每次写文章都折腾 Git 和命令行。

## 2021 年之后：从博客转向 GitHub Issues

2021 年，FarBox 到期了。

当时面临两个问题：

一是博客程序需要迁移，不能直接续费后继续使用；二是自己的工作重心已经从技术转向管理，技术对日常工作的帮助没有以前那么大了。

再加上很长一段时间没有写博客的习惯。

对于管理方面的内容，有些话也不太方便公开写出来，所以我没有再投入太多精力维护博客。

那段时间，我反而开始追求更简单的写作方式。

后来，我把文章迁移到了 GitHub Issues。

选择 Issues 的原因很简单：

- 可以直接在网页上写文章，不需要搭建本地环境。
- 支持 Markdown，代码块、图片等内容都比较方便。
- GitHub 的 Markdown 渲染效果不错，预览体验也很好。
- 文章本身就是 Issue，不需要额外维护一套博客程序。
- GitHub 是一个相对稳定的平台，不用太担心服务突然关闭，或者再次面临数据迁移。

对于只想记录技术内容的人来说，这种方式确实足够简单。

不过，使用一段时间后，新的问题也逐渐显现出来。

首先，GitHub Issues 无法直接绑定自己的域名；其次，页面样式和布局几乎无法按照自己的想法调整，搜索引擎优化（SEO）也比较受限。

另外，Issues 本身更偏向项目管理和交流，作为个人博客并不算理想。文章很少有人互动，博客也缺少一个真正属于自己的展示页面。

## 2026 年：借助 AI，自己做一个博客

随着 AI 编程工具越来越成熟，开发一个自己的博客已经没有以前那么困难了。

于是，我重新考虑了自己的博客需求。

这次，我不想再为了使用某个平台而接受它的各种限制，也不想回到 Hexo 那种每次写文章都要执行一堆命令的工作流。

我希望博客能够同时满足以下要求：

1. **支持自定义域名**：使用自己的域名，建立真正属于自己的博客。
2. **支持自定义样式**：页面布局、主题和前端样式都可以自由调整。
3. **文章数据可控**：写好的文章必须能够备份，最好直接保存为标准 Markdown 文件。
4. **平台稳定**：尽量依赖成熟的平台和基础设施，不希望以后又因为服务关闭而迁移。
5. **尽可能免费**：个人博客不应该承担太多服务器和流量成本。
6. **没有明显的流量限制**：不希望因为访问量增加就产生额外费用。
7. **可视化编辑**：最好直接在网页上写文章、预览和发布，不需要本地配置环境。

想了一圈，最终还是决定以 GitHub Issues 作为写作入口，再通过自动化程序解决博客展示和文章存储的问题。

于是，我开发了一个项目：

[issue-blog](https://github.com/raclen/issue-blog)

它的核心思路是：

- 在 GitHub Issues 中直接写文章，保留熟悉的 Markdown 编辑体验。
- 文章自动同步到 GitHub 仓库，保存为标准 Markdown 文件。
- 通过 Cloudflare 自动部署博客，使用自己的域名访问。
- 博客前端可以自定义样式和布局，不再受 GitHub Issues 页面限制。

这样一来，GitHub Issues 负责写作，GitHub 仓库负责保存文章，Cloudflare 负责部署和访问。

既保留了 Issues 简单方便的写作体验，又拥有了独立博客的域名、样式和 SEO 能力。

## 写在最后

从 2012 年的网易博客，到 Hexo、FarBox，再到 GitHub Issues，最后自己开发 issue-blog，前前后后已经折腾了十多年。

回头看，我对博客的需求其实一直没有太大变化：**写作要简单，文章要安全，数据要掌握在自己手里。**

以前为了实现这些需求，需要不断寻找合适的平台，在不同服务之间迁移。现在有了 AI 编程工具，终于可以按照自己的想法，把这些功能组合起来。

博客不一定要有多复杂，也不一定需要多少访问量。能够方便地记录自己的想法和技术经验，长期保存下来，就已经足够了。
